# Development diagnostic boundaries

Review safe development logging, renderer/preload failure telemetry or absence of a public logging API.

[Test implementation](../../../tests/desktop/logging.spec.ts) · [Flow patterns](../../patterns-flow.md)

## Starting conditions

A temporary profile with sentinel error/console values generated by the test. This is a nonvisual flow.

## Journey and assertions

1. Launch the real Electron app and verify its initial heading.
2. Emit main/renderer console events and renderer error/rejection events; poll the profile logs for fixed event records.
3. Emit a preload failure and verify the public bridge has no logging, filesystem or generic IPC entry points.
4. Close the app and verify safe structured rows, lifecycle events, request correlation and exclusion of private sentinel/error/path content.

## Run and refresh

```powershell
npm run test:desktop -- tests/desktop/logging.spec.ts --grep "@diagnostics( |$)"
```

The flow ID is also a test tag (`@diagnostics`); use `--grep "@diagnostics( |$)"` to select it exactly when names overlap. Passing runs replace only this flow's platform set and regenerate the table below. Failed/skipped/interrupted runs keep the previous references; inspect their age before relying on them. See the [maintenance workflow](../../patterns-flow.md#creating-or-changing-a-flow).

## Evidence limits

No screenshots are useful for the assertions; only a successful-run manifest is refreshed. Raw logs and injected private sentinels are not copied into reference directories.

Captures show Electron renderer content, without native title bars/menus. Any visible temporary absolute project paths are masked. Fixture account labels and learning text are synthetic. Visual references supplement the assertions and do not establish learning mastery or live-account access.
